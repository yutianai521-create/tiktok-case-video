# Event evidence and attribution

Use this for event-driven stories built from posts, emails, public logs, metrics, statements, or screenshots.

## One tension, one proof, one question

Build each short around:

1. One contradiction, consequence, or unanswered question.
2. One primary proof: original audio, email line, post, or public-log entry.
3. One landing that invites a specific judgment.

Two videos from the same event must use different tensions and different proof, not only different hooks.

## Evidence classes

- **Verbatim quote:** exact words from audio or text; quotation marks are allowed.
- **Paraphrase:** concise restatement; do not use quotation marks. Label `QUESTION PARAPHRASED` when useful.
- **Self-report:** an agent or person’s public log or statement; label the source.
- **Company statement:** the platform’s explanation of an incident; attribute it to the company.
- **Independent fact:** supported by a primary external record or independently verified source.

## Source labels

Keep labels small but visible:

- `SOURCE: X / @DIOSCURI`
- `PIP’S PUBLIC iLOG / SELF-REPORTED`
- `iLANDS POST-STREAM STATEMENT`
- `ORIGINAL AMA AUDIO / EDITED EXCERPT`

## Claim boundaries

Avoid stating that an agent is conscious, alive, dying, begging, fully autonomous, or independently verified unless the source establishes that claim. Prefer:

- `Pip said…`
- `Pip’s public log records…`
- `iLands said the livestream disconnected because…`
- `The post had passed one million views at the time of capture.`

For metrics, include the capture date or use a rounded milestone that remains true.

## Screenshot treatment

Show the complete source briefly, then enlarge only the relevant line. Preserve the sender/account identity and enough context to avoid turning a crop into a misleading quotation. Blur private addresses, payment details, internal IDs, and unrelated personal information.
